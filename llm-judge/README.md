# Week 4 P4 LLM judge add-on

Start with [REPORT.md](REPORT.md) for findings and [judge_analysis.ipynb](judge_analysis.ipynb) for executed, offline analysis. [METHOD.md](METHOD.md) explains policy choices, model selection, isolation and limitations. All artifacts in this folder are separate from the original customer-support submission.

## Run locally

From the Week-4 workspace in PowerShell:

```powershell
& ./p4/llm-judge/run.ps1 -Action verify
& ./p4/llm-judge/run.ps1 -Action analyze
& ./p4/customer-support/.venv/Scripts/python.exe -B -X utf8 ./p4/llm-judge/build_outputs.py
```

These commands use saved results and make no API calls. Python 3.10+ and its standard library are sufficient for analysis and artifact generation. The original project's existing environment is reused without modification. The notebook's code cells can run in any Python 3 Jupyter kernel; it uses no notebook-specific APIs. Its saved outputs were generated by executing the exact cell sources sequentially in a shared Python namespace; execution evidence is included.

To resume missing API assessments using the existing encrypted credentials:

```powershell
& ./p4/llm-judge/run.ps1 -Action pilot
& ./p4/llm-judge/run.ps1 -Action full
```

Completed validated judgments are reused without new API calls. A full run requires evidence/pilot_review.json with a reviewed PROCEED gate and the matching frozen rubric hash. The existing Windows-account-encrypted credential loader is imported without executing its classifier dispatcher. The wrapper clears credential environment variables on exit. Network access may require the execution environment's usual approval. No LangSmith feedback is added by this implementation.

## Files and reproducibility

- `rubric.txt`, `schema.json`, `config.json`: exact rubric, feedback schema, model snapshot and settings.
- `judge.py`, `run.ps1`: source preparation, authenticated model listing, pilot/full execution, strict validation and bounded retries.
- `inputs/`: immutable copies of the original prediction CSVs, authoritative final snapshot and annotation evidence, policy notes, and handout extraction. These contain synthetic ticket data and historical review context, never keys.
- `attempts/`: raw requests and responses or sanitized failures, one file per attempt. This includes rejected responses. `judgments/` contains the accepted structured assessment for every saved prediction.
- `results/summary.json`, `assessments.csv`, `paired_results.csv`, `review_needed.csv`, `disagreements.csv`: per-version aggregates, every assessment, paired differences and review queues.
- `evidence/`: model availability, immutable input/source hashes, pilot execution and review, full execution, validation and notebook execution evidence.
- `analysis.py`, `build_outputs.py`: offline analysis, report/notebook building, preservation checks and packaging.
- `artifact_manifest.json`, `llm-judge-addon.zip`: hashes and credential-free package for later GitHub inclusion. Nothing was pushed to GitHub.

To reproduce *new* model generations, create a new isolated output directory containing these code files, config and rubric, point SOURCE at the preserved customer-support project if necessary, run `prepare`, then the pilot, inspect its accepted rationales and write a new explicit pilot review gate before `full`. Never replace the existing freeze or accepted judgments. Sampling and service behavior can vary even with a pinned model and saved inputs. Reproducing the recorded analysis requires no API and is deterministic.

The handout recommends category-based calibration against human review. Here the frozen pilot checks the known mechanisms and categories, and post-hoc tables compare both original and reviewed labels. It does not claim independent human calibration, and does not automatically change any labels or approve cases. The 100 tickets come from 25 seed families. The final reviewed Exact Match result stays 93/100 versus 93/100.
