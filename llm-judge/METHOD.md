# LLM judge method and provenance

This optional add-on assesses the 200 preserved predictions from the fresh baseline and focused runs. It does not reclassify tickets or modify prior deliverables. All new artifacts live in this folder. `inputs/` contains exact copies of the saved run CSVs and authoritative review evidence, plus an extracted text copy of the handout. Input hashes and a hash inventory of the original project are in `evidence/freeze.json`.

## Handout requirements and deliberate adaptations

The optional handout judge sees query and predicted intent, excludes reference labels, returns 0/1 and one-sentence reasoning, and is compared with human judgments after human analysis and before/after comparison. Those prerequisites already exist. The add-on runs by code instead of clicking Playground controls, so requests and responses are reproducible and auditable. A pilot covers routing mechanisms and all five categories before all 200 saved assessments. This task explicitly requires a pilot; the handout's instruction not to click the UI Test button does not prohibit one. Existing participant failure categories are used for post-hoc analysis only. There is no label-agreement optimization loop or claim that approvals establish correctness.

## Rubric decisions

`rubric.txt` is the exact system message. Non-delivery plus refund routes to order_status; damaged goods plus refund routes to product_issue; missing money after a completed return and unwanted-order cancellation plus refund route to refund_request. Account help requires an actual account or checkout problem. Discounts and sales queries route to other. Underlying-problem precedence is a declared operational policy, supported by saved project policy notes, not an independent factual truth or a replacement for participant labels. It overlaps the focused classifier's intended rule and therefore evaluates adherence to that same policy; the judge is not policy-independent validation of that choice. Missing refund payments and cancellations also test overgeneralization of the rule. The participant's t046 refund_request label remains preserved in the reviewed-label comparison.

Ambiguity is distinct from correctness under the selected rule. A credible remedy-first alternative is flagged even when the policy gives one definite score. Ties between independent problems use emphasized current issue, then a declared deterministic order; they are flagged. Alternatives are advisory. Semantic ambiguity judgments may be unstable or influenced by the presented prediction.

## Model and settings

The original classifier used gpt-4o-mini, temperature 0. An authenticated model listing confirmed access before selection. The selected judge is gpt-5.4-mini-2026-03-17: a pinned available snapshot with Structured Outputs and a modest per-assessment cost. This is a practical choice for a small five-label task, not a demonstrated superiority claim. It is not the most capable available model. No alternate judge was selected to maximize the focused score. Low reasoning effort, max_completion_tokens 2048, store false, four concurrent requests, fixed shuffle seed, and up to three attempts per assessment are saved in config.json. Temperature is omitted for compatibility and the provider default applies; reproducibility means preserving inputs/settings/results, not guaranteed identical generations. No tools or external knowledge sources are supplied to the judge. Strict JSON Schema is paired with local field, type, enum, consistency, completion and refusal checks.

Current official OpenAI documentation was opened and checked during implementation:

- [GPT-5.4 mini model, snapshots, capabilities and pricing](https://developers.openai.com/api/docs/models/gpt-5.4-mini): snapshot choice, structured output support, reasoning settings, and published token rates.
- [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs): strict schema with additionalProperties false; refusals/incomplete output still need handling.
- [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices): clear criteria, pass/fail assessment, human calibration and judge bias concerns. The guidance to start with a more capable judge is weighed against the limited task and modest cost; this pilot does not establish human-level accuracy.

The model listing proves advertised account access; successful pilot calls verify invocation. Model docs are current web evidence, not a guarantee of future availability or unchanged pricing.

## Isolation, validation and analysis

The established Windows encrypted Read-SavedCredentials function is imported from customer-support/credentials.ps1 via its PowerShell AST. Only that function runs; its classifier/annotation action dispatcher does not execute. Secrets enter the child process environment and are cleared in finally. No key is copied to this folder or printed. The LangSmith key is loaded by the established loader but no LangSmith calls or writes are needed. Existing runs, feedback (75 verified records), queues (8/8 and 7/7), approvals, and labels remain untouched.

Requests contain only the same frozen rubric and a JSON user object with query and predicted_category. Ticket IDs, version names, run IDs, labels, human approvals, notes, EM results and aggregate scores remain local. Baseline and focused requests use exactly the same criteria, are independently assessed and shuffled. There is no cross-prediction deduplication; all 200 outputs receive their own assessment. Valid pilot judgments are reused once in the final 200, avoiding double counting. Raw API attempts retain returned usage even when output is rejected. Retrying validation failures may select a more internally consistent response, so rejected attempts are retained and counted, and failed calls with no returned usage have unknown cost. Each invocation permits up to three attempts per missing assessment; a deliberate resume keeps prior attempts and may add further bounded attempts. The initial full run was interrupted after transport stalls, with at most four in-flight requests lacking records. The timeout was shortened from 120 to 30 seconds without changing prompts or model settings. Subsequent calls write a STARTED record before sending. See evidence/transport_adjustment.json; exact total billing cannot be established from returned usage alone.

Post-hoc analysis compares both binary correctness and proposed intent with original and reviewed labels. All queries and predictions are checked against authoritative Fresh evaluation snapshot rows. The sole changed reference t046 is applied equally to both preserved outputs. Cross-version proposed-intent inconsistencies and ambiguity inconsistencies are measured as a limited sensitivity check. In 86 pairs the preserved predictions match, so the exact judge inputs are identical across the two independent requests; this provides a small repeatability check with only two calls per input, not a robust reliability estimate. t033 received conflicting proposed intents and scores for identical inputs; it remains unresolved for human adjudication rather than being rerun until a preferred answer appears. Confusion counts and grouped seed-family results are descriptive. The 100 synthetic tickets are paraphrases from 25 seed families, not independent held-out examples. No statistical significance or production generalization is claimed.

Review flags identify ambiguity, reference disagreement or inconsistent proposals, not auto-approved labels. Human approval means a case was reviewed. Judge scores are an additional policy-specific opinion. Disagreements may reflect routing policy choices, reference problems or judge error. Independent human adjudication and future held-out families are needed before scalable automated approval.
